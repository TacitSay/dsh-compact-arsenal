# dsh-compact-arsenal

**让长会话不再靠删历史续命。** 三个各自独立的压缩板块——整段检查点、思考压缩、工具输出压缩——每块有自己的触发阈值和处理方式，便宜的手段先用尽，再动用模型。左栏面板直接调，改完不用重启。

English | [中文](README.zh.md)

## 它解决什么问题

会话跑到几十万 token 之后，每一轮都在为「上个月那次找文件的输出」付钱。DSH 自带的压缩是**一次性整段摘要**：触发一次，前面的对话全被换成一份检查点，细节没了。

这个插件把「压缩」拆成三段，让你自己决定每段怎么处理：

| 板块 | 压缩什么 | 默认方式 | 花不花钱 |
|---|---|---|---|
| **工具输出压缩** | 旧轮次里超长的 `tool/result` 正文 | 按字符预算截头留尾 | ❌ 零模型调用 |
| **思考压缩** | 旧轮次助手消息里的 `reasoning` 块 | 模型写要点 | ✅ 触发时一次 |
| **总压缩** | 最旧的若干**整轮**对话 | 模型写检查点 | ✅ 最贵，最后才跑 |

---

## 快速开始

```sh
dsh plugin --profile <你的profile> add dsh-compact-arsenal
```

重启后左栏出现**「上下文压缩」**图标。

**所有板块默认关闭**——装上不改变任何行为，这是刻意的。

打开面板，先只开「工具输出压缩」，阈值保持 0.6。它会用最便宜的方式把大头处理掉。

> 想先在插件市场看？条目已提交到 [awesome-dsh-plugin](https://github.com/awesome-dsh-plugin/awesome-dsh-plugin) 与 [awesome-deepseek-harness-plugins](https://github.com/imsai-sh/awesome-deepseek-harness-plugins)。

## 压缩是怎么做的

### 执行顺序：便宜的先来

这不是三个独立的开关，是一条**级联**：

```
工具输出（机械，零成本）
   ↓ 每步之后重新测量压力
   压力还高？
   ↓
思考压缩（模型）
   ↓ 重新测量
   压力还高？
   ↓
总压缩（模型，改写整轮）
```

**每一步做完都会重新测量。压力降到下一步阈值以下就停下。**

这正是官方 `dsh-compaction-tool-result-pruner` 的做法——它也是「先剪、重测、够了就不调模型」。意义很实际：多数情况下**只剪工具就够了**，后面两次模型调用根本不发生。

### 各板块细节

**工具输出压缩**

单个工具结果超过 8192 字符时，保留头 4096 + 尾 1024，中间换成标记：

```
（前 4096 字符原样保留）

[... tool result middle pruned ...]

（后 1024 字符原样保留）
```

原始内容完整保留在会话日志里，可回查。

**思考压缩**

模型的思考是碎片化的——一条 8000 字的思考很少见，多是几百到一两千字散在几百条消息里。所以按「单条超过 N 字」判定几乎永不触发。

这里按**总量**判定：把所有旧碎片加起来超过 `minTotalChars`（默认 15000 字）才动手，然后**打包成一次模型调用**（每批最多 8 条、合计 12000 字符），模型返回逐条要点。

**总压缩**

最旧的若干整轮对话换成一份结构化检查点，按 `##` 分节记录：目标、涉及的文件与命令、报错与修法、已完成与待办、下一步。

按**整轮**替换，保证工具调用与结果始终成对进出。

### 触发条件

三件事同时满足才动手：

```
本板块开关打开
AND 上下文压力 ≥ 本板块阈值
AND 目标内容总量 ≥ 本板块下限
```

阈值是**上下文窗口占用比例**，不是绝对字符数。100 万窗口 × 0.6 = 60 万 token。

## 效果

以下数字来自一次真实会话的压缩归档（`trae/deepseek-v4.1-flash`，100 万窗口），**不是估算**：

| 板块 | 次数 | 压缩前 | 压缩后 | 省下 | 比例 |
|---|---|---|---|---|---|
| 工具输出（机械） | 61 | 149,019 | 121,332 | 27,687 | 18.6% |
| 思考（模型） | 47 | 87,674 | 46,916 | 40,758 | 46.5% |
| 总压缩（模型） | 1 | 60,185 | 2,657 | 57,528 | **95.6%** |
| **合计** | **109** | **296,878** | — | **125,973** | **42.4%** |

几条最值得看的单例：

```
总量压缩   60,185 → 2,657    (省 95.6%)
工具输出   49,930 → 5,366    (省 89.3%)  ← 一条 uvicorn 访问日志，关键的 NameError 在尾部被保留
工具输出   15,958 → 5,406    (省 66.1%)
思考        7,795 → 1,163    (省 85.1%)
```

**注意这些比例的差异是有意义的**：

- 工具输出只省 18.6%——因为大多数工具结果本来就比预算小，只有少数超长的被处理；
- 思考省 46.5%——模型写要点比机械截断更彻底；
- 总压缩省 95.6%——整轮对话换成一份检查点，压缩率最高，但**信息损失也最大**。

**压缩记录全部落盘**（可选关闭），文件名形如：

```
archive/压缩--session-5fd2…/reasoning--model--20261113-232318--seq2591.md
```

每份含：原文字符数、改写后字符数、节省比例、模型要点、改写后内容、完整原文。

## 你可能担心的事

写在这里，因为这些问题我自己踩过。

### 「压缩会不会把重要内容删掉？」

工具截断保留头尾，中间才是被丢的部分。日志类输出的中间几乎全是重复行。

**但这不是保证。** 如果你有一条命令的输出「中间恰好是关键信息」，它会被剪掉。缓解办法：

- 调大 `headChars` / `tailChars`；
- 或把该段改用模型方式，让模型判断什么该留。

原始内容始终在会话日志里，可以通过 `sourceEventSeqs` 定位回原文。

### 「反复压缩会不会一直烧钱？」

不会，三道阻断：

1. **幂等标记**——压过的内容带标记，下次直接跳过，永不重复压；
2. **单项下限**——压完已经短了，不达门槛就不再是候选；
3. **每轮预算**——一次触发最多占用 90 秒（`maxPassMs`），超了停手。

再加上级联短路，多数轮次根本走不到模型。

### 「压缩会让缓存失效吗？」

**会，但只在你压缩的那一刻。**

Prompt 缓存靠前缀匹配工作。压缩改写了前面的内容，其后全部失效，下一次请求要重建缓存。

级联设计缓解了这一点：`keepLast` 保留最近 2–3 条不动，所以**最近的前缀始终稳定**；工具压缩只作用于旧节点，越靠前的东西动得越少。

> 如果你的渠道显示缓存命中率一直是 0，先确认它是否**上报**这个字段。我在排查时发现某些中转渠道（如 `trae/*`）的 671 次调用里一次都没上报 `cacheReadTokens` —— 那不是缓存失效，是根本没有数据。

### 「会不会把会话搞坏？」

这个插件出过两次事故，都是写日志时形状不对：

| 事故 | 症状 | 原因 |
|---|---|---|
| #1 | 会话打不开 | 替换行写了当前 turn，而 DSH 要求工具结果「只能改 content」 |
| #2 | 会话打不开 | `user/message` 检查点漏了 `id` 字段 |

**两次都已修复**，并且现在有两类测试守着：

- `test/turn-shape.test.mjs`——**在 turn 打开的条件下**验证两种替换形状（这正是当初所有离线检查漏掉的条件）；
- `test/checkpoint-shape.test.mjs`——用打包的 `dsh-session` 真实写入并校验。

另有 `verify-fix.cjs` 做 24 项源码断言。**60 个测试，全绿。**

### 「压缩了但我看不出效果」

打开**压缩留存**，每次改写都会落盘。面板底部显示归档目录和运行日志路径。

日志里有 `gate`（门槛判定）、`cascade step`（谁动手了）、`cascade skip`（谁被短路跳过）——能直接看出「为什么没压缩」。

## 面板

左栏「上下文压缩」，四个部分：

- **三个板块**：开关、方式卡片、阈值参数。改完 500 ms 自动保存并热重载；
- **压缩留存**：是否落盘、归档目录、「打开目录」按钮、运行日志路径；
- **状态行**：本次执行了哪些、省了多少、失败几次及原因；
- **版本徽章 + 检查更新**：查询 npm 上是否有新版本。

## 配置

也可以直接写 profile 的 `cordis.patch.yml`：

```yaml
- id: compact-arsenal
  name: dsh-compact-arsenal
  config:
    enabled: true
    archiveEnabled: true
    total:
      enabled: true
      pressureRatio: 0.8        # 最后才跑
      retainTurns: 2
      provider: ''              # 留空 = 跟随当前会话模型
      model: ''
    reasoning:
      enabled: true
      pressureRatio: 0.7
      mode: model               # truncate | clear | model
      minTotalChars: 15000      # 总量门槛
      keepLast: 3
    tools:
      enabled: true
      pressureRatio: 0.6        # 最先跑，最便宜
      mode: truncate            # 机械，零模型调用
      thresholdChars: 8192
      keepLast: 2
```

**建议的阈值关系**：`tools < reasoning < total`。这样便宜的先跑，贵的只在必要时才跑。
